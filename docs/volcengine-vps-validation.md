# Volcengine SeedDuplex on the public Dots demo

## Runtime path

The public demo at `https://codex.cokeagent.com/dots-demo/` is served through the existing tunnel to the Mac demo process on `127.0.0.1:14318`. The browser calls the same-origin `/dots-demo/api/voice/provider` and opens `/dots-demo/api/voice-calls/:id/volcengine-stream`; the server holds the SeedDuplex API key from the mode-0600 `demo.env` and proxies the WebSocket to Volcengine. The browser never receives the provider key. Voice transcripts are submitted to the tenant-owned call-turn endpoint and then dispatched to the selected Agent kernel.

The VPS demo default Agent kernel remains **Pi**. Voice provider selection is independent of the Agent kernel.

## Automated public browser test

Use a dedicated Google test account and the mode-0600 storage state generated by `npm run test:e2e:public-demo:auth-setup`:

```sh
DOTS_PUBLIC_DEMO_STORAGE_STATE="$HOME/.local/state/coke-dots/public-e2e-state.json" npm run test:e2e:public-demo:voice
```

This launches Chrome with a generated all-zero WAV as its fake microphone. It clicks **拨打 Dot**, checks the authenticated provider and SeedDuplex session, keeps the speaker enabled, sends a Chinese text-to-speech phrase, and verifies that non-silent PCM is scheduled through a running Web Audio context to Chrome's speaker destination. It saves the exact returned audio as `assistant-reply.wav`, clicks **结束通话**, and checks that the call ended. It never opens the physical microphone or creates an Agent task.

For the full public voice-to-cloud-Agent path, use:

```sh
DOTS_PUBLIC_DEMO_STORAGE_STATE="$HOME/.local/state/coke-dots/public-e2e-state.json" npm run test:e2e:public-demo:voice-agent
```

This feeds a generated Chinese WAV to Chrome's fake microphone, checks the recognized request, dispatches exactly one Pi task, verifies that the ready tenant Linux computer opened `example.com`, and checks the Chinese task result was returned as audible PCM to the speaker output path. It also saves that reply as `assistant-reply.wav`. It does not use BlackHole or the room microphone. Both scripts write a redacted manifest with a tenant hash and response statuses. If the dedicated state file is absent, the authenticated test does not run.

## Playback interruption finding

The SeedDuplex protocol maps `response.output_audio.started` to the assistant's `TTSSentenceStart` event. The previous gateway forwarded it as `speech-started`, which the browser treats as user speech and responds to by stopping all queued assistant audio. The gateway now sends `assistant-speech-started` for that event, leaving the playback queue intact; only the input-transcription start event clears playback. The previous public smoke test also turned the speaker off and checked only that PCM bytes arrived, so it could pass while users heard nothing. The revised test keeps the speaker on and verifies Web Audio scheduling and its connection to Chrome's speaker destination. [Volcengine SeedDuplex event reference](https://docs.volcengine.com/docs/DoubaoVoice/access-mustread?lang=zh).

The public domain currently reaches the Mac demo process through the existing tunnel. This makes the service reachable from the public domain, while the process itself is not hosted on the VPS.

## SeedDuplex protocol detail

For text-to-speech smoke requests, send the text in the `speech_text_buffer.commit` event. Sending an empty `speech_text_buffer.replacement.commit` after an append can create the session but leave it with no speech to synthesize. A regression test covers the required event payload.

For ASR, live SeedDuplex `conversation.item.input_audio_transcription.delta` messages were observed to contain the complete transcript-so-far, not an append-only token. They can revise punctuation or shorten an earlier partial. Keep the newest non-empty snapshot; concatenating these snapshots duplicates earlier words. The `completed` event can omit `transcript`, so retain the latest snapshot as the final fallback.

The task follower EventSource must be built with `appPath('/api/events')` because the public application is mounted under `/dots-demo/`; a root-relative `/api/events` resolves outside the deployment prefix and receives the HTML app shell instead of the event stream.

## PCM format mismatch and playback check (2026-10-13)

- Root cause found for the reported static: SeedDuplex `session.audio.output.format.type` requested `pcm` (24 kHz float32), while `session.extension.tts.audio_config.format` requested `pcm_s16le` (24 kHz signed 16-bit). The browser's marker-2 path decodes float32. If the provider honored the extension format, those int16 bytes would be interpreted as float samples and sound like static. The server's previous “looks like float32” heuristic was not enough to detect this mismatch.
- SeedDuplex now sends `pcm` in both format fields. The legacy O2.0 session keeps its existing `pcm_s16le` output.
- Live SeedDuplex smoke with the aligned format returned first audio at 518 ms, 90,985 float32 samples at 24 kHz, RMS 0.08770, peak 0.29596, with no malformed frames or invalid samples.
- After deployment, signed-in Chrome on the public URL clicked **拨打 Dot**, opened the real SeedDuplex WebSocket, sent a Chinese speech test to the real provider, and scheduled all 14 returned audio buffers through Web Audio. The provider data used marker 2, contained 129,645 float32 samples at 24 kHz, had no invalid samples, and all 14 browser audio sources ended. Public and local JS both served `index-X1lGPV-L.js`, SHA-256 `7b45370c3163ca676e1586fb542559c65abd6edd4ebd04e24bcfbdbd53f483da`.
- `npm test`: 133 passed. `npm run test:e2e`: 53 Chrome UI steps and 8 cloud-computer checks passed. `npm run build:demo`: passed.
- Before restarting, authenticated `/api/state` showed zero active calls and no tasks in a running state. SQLite `PRAGMA quick_check` returned `ok`.
