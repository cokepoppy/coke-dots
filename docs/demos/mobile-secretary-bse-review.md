## 电话脚本

### 1. 让 Dot 找到现有会议资料

用户说：

> 请查一下北交所交易规则变更评审的日程、我已有的会后语音速记和关联待办。告诉我日程时段是否已过，概括速记里记录的规则要点，以及两条待办是否完成和截止时间；先只读，不要修改任何数据。

Dot 必须从公网对话中实时读取并引用匹配的日程、现有速记和待办。建议回答：“日程是 10 月 19 日 08:00–08:45，时间已过；我找到《会后语音速记》，其中记录了 10 月 26 日生效日、70%/130% 与成交价极值约束、10 万股或 100 万元门槛；两条待办仍未完成，分别在 10 月 20 日和 21 日 17:00 截止。”以当场读取为准。`confirmed` 不是结束状态；不要说这条音频刚在会议后生成，也不要朗读摘要中的过时“会前准备/即将评审”小标题。不要重建、修改日程、听记或待办。

用户说：

### 3. 让用户看页面，再创建 PR

Pi 先在云电脑 Chromium 展示最终页面，口头报告实际 URL、页面标题、改动点和测试结果。用户确认看到的内容后说：

> 页面我看到了。请创建这个分支的 GitHub Pull Request，把链接和测试结果告诉我；保持 PR 未合并。

PR 应以最新 `main` 为 base，包含本次必要代码与测试，列出听记依据和实际测试命令；不自动合并、不部署、不发交易委托。若没有新的代码差异，不创建空 PR；若同一差异已有未合并 PR，复用并报告该 PR，不再制造重复 PR。

## 节奏与超时处理

预计现场段落为 7–12 分钟，尚未通过完整实机流程计时，不能当作保证时长。下表是各阶段的提示性节奏；云端修改与测试可能占用 3–7 分钟，不能为赶时间跳过验证。会前至少做一次完整计时彩排：

| 阶段 | 建议用时 | 现场重点 |
| --- | ---: | --- |
| 拨通与中文提问 | 15–30 秒 | Dot 确认开始查询；没有长时间静默 |
| 查会议、听记、待办 | 30–60 秒 | 报真实来源、结论、负责人和截止时间 |
| 派工与审查仓库 | 30–60 秒 | 显示从最新 `main` 创建的分支和实际任务范围 |
| 修改与测试 | 3–7 分钟 | 投影云电脑实时操作；语音或任务进度用真实阶段状态更新 |
| 页面验收与 PR | 1–2 分钟 | 展示真实 URL/标题/页面，再创建未合并 PR |

如果单阶段超出 60 秒，Dot 应简短说明当前真实进度，用户可继续让它后台工作；不得播放预制成功话术、伪造进度或为了控时跳过测试。若总时长对领导场景仍太长，应在彩排后优化仓库启动/依赖缓存和任务目录准备，不预先完成代码修改来冒充现场执行。

## 可重复运行与复位

1. 日程、AI 听记和待办是用户的真实记录，整个演示过程只读；复位绝不删除或重建它们。
2. 每轮使用新的 Dot 对话、任务 ID 和云电脑任务目录。只有确认存在新的代码要求时，Pi 才从重新 fetch 的最新 `origin/main` 创建功能分支；不要把新任务目录误当作需要重复造一个功能分支。若同一要求的相同差异已有未合并 PR，可在干净任务目录重演分析、修改和测试，但最终复用该 PR 链接，不能重复开 PR。
3. 每轮从最新 `main` 开始，不回退 `main`、不 force-push、不清理整个租户 PVC。清理范围仅限已验证的本轮任务工作目录；当前还没有经公网 Chrome 验证的专用复位按钮，因此正式演示前需证明新任务会得到干净目录。
4. PR 保持未合并。若把 PR 合入 `main`，相同需求下次运行已不再是新改动；重演必须基于新的真实会议结论，或另行建立经过用户认可的独立演示仓库，不能把旧 main 当“最新 main”。若 PR 仍未合并且差异相同，复用它作为演示结果；新结论带来不同差异时，再从当时最新 `main` 拉新分支。
5. 屏幕截图和录屏保存在项目内 `artifacts/demo/mobile-secretary-bse/<run-id>/`。每张图标注阶段、时间、来源（真实公网 Chrome 或本地测试）；隔离 E2E 图不得标成公网验收图。完整验收后再将图集发送到用户的钉钉。
