It identifies Slack direct messages and channel mentions in threads as supported ways to contact the Dot. By default, the Dot replies to the user; sharing context from a private conversation with other people needs permission. Adding a Dot to a channel does not itself configure monitoring. Source: [Message your dot](https://learn.chatgpt.com/docs/dots/channels).

## Implementation boundary

Coke Dots shows the observed “Workspace” placeholder and “Select a workspace” action before a Slack installation exists. That action starts OAuth without a `team` parameter; after the callback returns ASPI, the modal shows “Add to Slack” to link that workspace to the active Dot tenant. Slack documents that omitting `team` lets the user choose a workspace during authorization ([OAuth v2](https://docs.slack.dev/authentication/installing-with-oauth/)). The video confirms the initial and selected states but does not show the trigger, consent page, or transition; mapping the first action to OAuth remains an implementation choice. The video does not show workspace switching, channel monitoring controls, or the “More Slack settings” section; those remain Coke Dots implementation extensions rather than pixel-verified Dots UI.

The modal implements a Slack OAuth v2 workspace installation flow requesting `chat:write`, `app_mentions:read`, `im:history`, `im:write`, `channels:read`, and `channels:history`. The public-channel scopes support the opt-in monitor described in [proactive Slack monitoring](slack-proactive-monitoring.md); existing Slack installations must reauthorize to receive these added scopes. OAuth state is one-use, ten-minute, and bound to the signed-in user and active tenant. Bot tokens are stored in macOS Keychain under a tenant-and-Slack-team-derived account name; SQLite stores only installation metadata and granted scopes. Selecting a contact workspace is tenant-scoped, and only workspace owners or admins can connect or change it. The Slack identity that completes OAuth is linked to that Coke Dots member. A member can inspect the current shared selection.

The message bridge accepts `message.im` and `app_mention` events at `/slack/events`. It verifies Slack's HMAC signature against the raw body, rejects timestamps more than five minutes old, and deduplicates by Slack `event_id`. The handler stores an event and tenant-scoped task before returning; the background worker then runs the task and posts its final, waiting, or failed result through `chat.postMessage`. Direct messages reply to their existing DM channel. A channel mention opens a private 1:1 app DM using `conversations.open` (`im:write`) before posting, so it does not publish the result in the source channel. Delivery retries are bounded, honor Slack's `Retry-After` response, and become visible as dead-letter rows after five attempts. Direct messages and mentions are accepted only for the Slack identity linked during OAuth. If the same Slack sender resolves to more than one selected Coke Dots tenant, the event is ignored rather than dispatched ambiguously.

The server needs `SLACK_SIGNING_SECRET`, and the Slack app's Events API must point to the publicly reachable `/slack/events` URL with the `app_mention` and `message.im` bot events subscribed. Reauthorize existing installations to grant the added scopes. The `/api/slack` status shows whether the signing secret is configured; it cannot confirm that the Slack developer console has the correct request URL and subscriptions. Slack documents `chat:write` for sending messages, `im:write` for opening a 1:1 DM, and app mention/DM event subscriptions; the request verification guide defines the signed raw-body validation used here. See [Slack OAuth v2](https://docs.slack.dev/authentication/installing-with-oauth/), [Slack request verification](https://docs.slack.dev/authentication/verifying-requests-from-slack/), [`conversations.open`](https://docs.slack.dev/reference/methods/conversations.open/), [`chat.postMessage`](https://docs.slack.dev/reference/methods/chat.postMessage/), [app_mention event](https://docs.slack.dev/reference/events/app_mention/), and [message.im event](https://docs.slack.dev/reference/events/message.im/).

## Verification

The Chrome UI E2E uses a local-only mock Slack provider. It asserts the “Workspace” placeholder and “Select a workspace” CTA in both light and dark themes, follows mocked OAuth, verifies the returned ASPI-selected state and “Add to Slack” CTA, and links the selected workspace; advanced controls remain collapsed. The same browser run sends signed DM and channel-mention events, waits for the task worker, verifies the result, and confirms that DM replies return to their source conversation while channel mentions receive a private app DM. It also tests proactive monitor setup, event review and deduplication, pause/resume, tenant isolation, and shared-workspace permissions. Unit tests cover HMAC validation (including stale timestamps and altered bodies), tenant identity mapping, duplicate delivery, ambiguous sender rejection, and queueing results. These tests verify local fixtures; they do not exercise a live Slack app, hosted consent page, or Slack-delivered event. The video confirms selected visual states but not the OAuth transition.
