# Slack contact setup: evidence and implementation boundary

It says the Dot replies to the initiating user by default; sharing private conversation context with other people requires permission. Adding the Dot to a channel does not by itself configure channel monitoring. Source: [Message your dot](https://learn.chatgpt.com/docs/dots/channels).
- John Aspinall's V2 video (`Q9tF0R8d_Co`) was rechecked in Chrome on 2026-10-11 by pausing and stepping through the player. At 07:14, the conversation and call-ended chip are visible without the Slack modal. At 07:19, “Set up Slack” is open with a Slack-icon “Workspace” placeholder, helper text “Choose the workspace to add Roger to Slack,” a green “Select a workspace” button, and a close control. At 07:21, the same modal remains open with its workspace menu expanded: “Choose a workspace,” “ASPI,” and “Select another”; the primary action still reads “Select a workspace.” At 07:24, ASPI is selected in the collapsed picker and the primary action reads “Add to Slack.” These samples bound the visible picker transition; they do not prove which click caused it.
- The video is compressed and composite. In the embedded application frame, the dialog is visibly docked near the upper-left (about 1.4% of viewport width from the left and 22% of viewport height from the top); its displayed width is about 440 capture pixels. These are frame-relative estimates, not source CSS dimensions. The video supports the sampled labels, menu items, selection state, CTA change, and broad layout. The click opening the modal, Slack's hosted consent, the OAuth callback, and inbound/outbound Slack messages are not shown clearly. Source frames were inspected live in Chrome but were not retained as PNG files.
- The installed Slack desktop app was inspected read-only to identify the local client. Its channel UI is Slack itself and is not evidence for Dots' Slack setup modal; no Slack message was sent or changed.

## Current implementation

Coke Dots reproduces the observed details-panel Slack action and workspace setup modal. The local OAuth v2 flow requests `chat:write`, `im:history`, `im:write`, and `app_mentions:read`, uses one-time state bound to the signed-in user and active tenant, and stores the workspace bot token in macOS Keychain under a tenant-and-team-derived entry. SQLite stores installation metadata and scopes, not the token. Workspace selection is tenant scoped; only owners and admins can connect or change it. After OAuth returns an installed workspace, the modal shows the “Workspace” placeholder and “Select a workspace” action, then exposes the observed picker entries. Choosing an installed workspace changes the primary action to “Add to Slack.” The dialog's upper-left viewport placement follows the compressed video frame; its measurements are estimates, not source CSS pixels.

The video does not show the exact authorization transition. Coke Dots uses Slack OAuth v2 as an implementation choice: “Select a workspace” starts OAuth, the callback returns to the setup modal, and “Add to Slack” links the selected workspace to the Dot. The local E2E consent page is a mock and does not verify Slack's hosted consent screen.

The Events API bridge at `/api/slack/events` accepts signed `message.im` and `app_mention` callbacks. Configure the server-side `SLACK_SIGNING_SECRET` and set Slack's Events API Request URL to the public HTTPS endpoint ending in `/api/slack/events`. The route handles Slack URL verification, verifies HMAC against the raw request body and a five-minute timestamp window, limits payload size, rejects malformed or unsupported events, deduplicates event IDs, and acknowledges callbacks before starting Agent work. A Slack user must first link their own Coke Dots account through a single-use, expiring link sent by private DM; unlinked messages do not create tasks. Linked DMs can create tasks or continue a waiting task when replied to in its thread. Channel mentions create tenant tasks and deliver the result privately to the requesting user by default. A persistent outbox retries transient Slack delivery failures. This follows Slack's acknowledgement/retry contract and Dots' private-reply default; it does not enable scheduled channel monitoring or authorize arbitrary external writes. The Events API behavior is based on official API documentation and local tests, not a video-observed workflow. Sources: [Slack Events API delivery and retries](https://api.slack.com/apis/connections/events-api), [Slack URL verification](https://api.slack.com/events/url_verification), [Slack `message.im`](https://docs.slack.dev/reference/events/message.im/), [Slack `app_mention`](https://docs.slack.dev/reference/events/app_mention/), [Slack request verification](https://docs.slack.dev/authentication/verifying-requests-from-slack/), [Slack `conversations.open`](https://docs.slack.dev/reference/methods/conversations.open/), [Slack `chat.postMessage`](https://docs.slack.dev/reference/methods/chat.postMessage/), and [Dots channels](https://learn.chatgpt.com/docs/dots/channels).

## Verification

`npm test` covers OAuth state, tenant isolation, account linking, DM task creation/resume, mention routing, signature replay/tamper rejection, and malformed JSON. `npm run test:e2e` exercises the setup modal with loopback-only mock Slack OAuth, then posts signed synthetic Events API callbacks to verify private-DM linking, DM task creation/continuation, channel-mention private delivery, and event deduplication in Chrome. The UI flow also checks the measured picker states, light/dark rendering, token storage outside the API/SQLite, tenant isolation, and owner/member permissions. These tests verify Coke Dots' local implementation; they do not verify Slack's hosted consent screen or live event delivery.

The event bridge requires a live Slack app with the documented event subscriptions, scopes, signing secret, and public HTTPS Request URL. No live Slack authorization or message delivery has been claimed.

After integrating the latest mainline UI on 2026-10-11, this branch passed `npm test` (60/60), `npm run build`, and `npm run test:e2e` (36 Chrome UI steps plus all 8 cloud-computer checks). The browser run covers the measured workspace picker states in light and dark themes and the signed synthetic Events API flow. Artifacts are under `artifacts/e2e/2026-10-11T12-43-27-991Z/` and `artifacts/e2e/linux-cloud-computer-2026-10-11T12-45-24-367Z/`. These remain local fixture tests, not proof of live Slack authorization or event delivery.
