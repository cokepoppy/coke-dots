# Slack contact setup: evidence and implementation boundary

## Product evidence

- Official Dots documentation describes one Dot reachable through connected contact methods, including Slack direct messages and channel mentions. It says the Dot replies to the initiating user by default; sharing private conversation context with other people requires permission. Adding the Dot to a channel does not by itself configure channel monitoring. Source: [Message your dot](https://learn.chatgpt.com/docs/dots/channels).
- John Aspinall's V2 video (`Q9tF0R8d_Co`) was rechecked in Chrome on 2026-10-11 by pausing and stepping through the player. At 07:14, the conversation and call-ended chip are visible without the Slack modal. At 07:19, “Set up Slack” is open with a Slack-icon “Workspace” placeholder, helper text “Choose the workspace to add Roger to Slack,” a mint pill-shaped “Select a workspace” button, and a close control. At 07:21, the same modal remains open with its workspace menu expanded: “Choose a workspace,” “ASPI,” and “Select another”; the primary action still reads “Select a workspace.” At 07:24, ASPI is selected in the collapsed picker and the primary action reads “Add to Slack.” These samples bound the visible picker transition; they do not prove which click caused it.
- The video is compressed and composite. In the embedded application frame, the dialog is visibly docked near the upper-left (about 1.4% of viewport width from the left and 22% of viewport height from the top); its displayed width is about 440 capture pixels. The mint CTA has a pill-shaped silhouette; its CSS radius is approximated as 22 px on the 41 px local control. These are frame-relative estimates, not source CSS dimensions. The video supports the sampled labels, menu items, selection state, CTA shape, and broad layout. The click opening the modal, Slack's hosted consent, the OAuth callback, and inbound/outbound Slack messages are not shown clearly. Source frames were inspected live in Chrome but were not retained as PNG files.
- The installed Slack desktop app was inspected read-only to identify the local client. Its channel UI is Slack itself and is not evidence for Dots' Slack setup modal; no Slack message was sent or changed.

## Current implementation

Coke Dots reproduces the observed details-panel Slack action and workspace setup modal. The local OAuth v2 flow requests `chat:write`, uses one-time state bound to the signed-in user and active tenant, and stores the workspace bot token in macOS Keychain under a tenant-and-team-derived entry. SQLite stores installation metadata and scopes, not the token. Workspace selection is tenant scoped; only owners and admins can connect or change it. After OAuth returns an installed workspace, the modal starts with the “Workspace” placeholder and “Select a workspace” action; the user opens a custom menu, chooses an installed workspace, then sees “Add to Slack.” The sampled menu also includes “Select another,” which starts a new OAuth attempt in Coke Dots. The dialog's upper-left viewport placement follows the visible composite-frame estimate. The video does not show Slack's hosted authorization or message delivery.

The video does not show how its authorization transition works. Coke Dots uses Slack OAuth v2 as an implementation choice: the “Select a workspace” click begins the OAuth flow; after callback, the same modal shows installed workspaces and “Add to Slack” links the selected workspace to the Dot. The local E2E's consent page is a mock and does not resemble or verify Slack's hosted consent screen.

On 2026-10-13, a signed-in Chrome click opened the public Slack setup dialog, which reported “Slack connection is not configured for this build.” No OAuth request was started. This describes the current public deployment and does not invalidate the local mock-backed feature flow.

This branch does **not** receive Slack Events API messages, create tasks from Slack messages, or send Dot responses to Slack. Selecting a workspace is not evidence that Slack conversations work end to end. A tenant-scoped signed event bridge is a separate feature and must verify Slack signatures, timestamps, identity bindings, event deduplication, and private delivery behavior before it is enabled. See [Slack OAuth v2](https://docs.slack.dev/authentication/installing-with-oauth/) and [Slack request verification](https://docs.slack.dev/authentication/verifying-requests-from-slack/).

## Verification

`npm run test:e2e` exercises a Chrome click-through using a loopback-only mock Slack OAuth provider: open the modal, start authorization, approve the mock consent, return through the callback to an unselected ASPI workspace, expand the picker, inspect its three options, select ASPI, and add it to the Dot. It verifies the token is held by the isolated E2E Keychain service and absent from the API and SQLite, confirms a separate Google tenant sees no installation, checks owner/member write permission, and captures light/dark plus picker-state screenshots. These checks cover local fixtures, not Slack's hosted page or a live Slack installation.

On 2026-10-11, the updated branch passed `npm test` (57/57), `npm run build`, and `npm run test:e2e` (35 Chrome UI steps plus 8 cloud-computer checks); the Chrome UI run passed all 35 steps again after the final menu-state screenshot changes. The latest screenshots are under `artifacts/e2e/2026-10-11T10-26-59-516Z/screenshots/`; they include the empty modal in light and dark themes, the post-OAuth available-workspace state in both themes, the expanded menu in both themes, and the selected ASPI state. These screenshots verify Coke Dots' implementation and transitions, not pixel parity with the compressed YouTube source.

After integrating the current mainline on 2026-10-13, `npm test` passed 66/66, `npm run build` passed, and `npm run test:e2e` passed 37 Chrome UI steps plus all 8 cloud-computer checks. Fresh artifacts are under `artifacts/e2e/2026-10-13T05-09-32-238Z/` and `artifacts/e2e/linux-cloud-computer-2026-10-13T05-11-38-098Z/`.
