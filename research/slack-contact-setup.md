# Slack contact setup: evidence and implementation boundary

## Product evidence

- Official Dots documentation describes one Dot reachable through connected contact methods, including Slack direct messages and channel mentions. It says the Dot replies to the initiating user by default; sharing private conversation context with other people requires permission. Adding the Dot to a channel does not by itself configure channel monitoring. Source: [Message your dot](https://learn.chatgpt.com/docs/dots/channels).
- John Aspinall's V2 video (`Q9tF0R8d_Co`) was replayed in Chrome on 2026-10-13 around 07:14–07:23. The captured frames show the Dots computer and the “Set up Slack” dialog. The visible dialog has a centered title and close control, a large inset workspace card, the centered “Your dot in” workspace selector with ASPI, the helper “Choose the workspace to add Roger to Slack,” and a mint “Add to Slack” button. The selector is closed in the two frames directly rechecked during this pass. No Slack icon appears above the title.
- An earlier note described “Select another” and “Select a workspace” as visible in this interval; the direct Chrome replay now shows “Add to Slack” and does not show that text. The earlier description is superseded for these sampled frames. No continuous click recording or original PNG has been retained, so the exact selector menu contents and post-click state remain uncertain.
- The compressed composite supports the broad hierarchy and approximate proportions, not exact CSS values. The Dots screen occupies about 765 × 433 pixels within the video; the dialog about 220 × 185 and its inset card about 194 × 110. These are approximate video-frame measurements and should be used for aspect and spacing checks only. The click opening the modal, Slack's hosted consent, OAuth callback, completed installation, and inbound/outbound Slack messages are not shown clearly.
- In the signed-in public Chrome session at `https://codex.cokeagent.com/dots-demo/`, clicking the Slack action opened the dialog, which displayed “Slack connection is not configured for this build.” This proves the public UI route only; it does not prove public Slack OAuth. The signed-in public app currently lacks the Slack integration configuration.
- The installed Slack desktop app was inspected read-only to identify the local client. Its channel UI is Slack itself and is not evidence for Dots' Slack setup modal; no Slack message was sent or changed.

## Current implementation

Coke Dots matches the observed dialog hierarchy with a centered title, no icon above the title, a large inset workspace card, the four-color Slack mark in the selector, the observed helper, and a mint pill action. At a 1440 × 1000 Chrome viewport the dialog is 440 × 365 and the card is 390 × 220; these are implementation measurements chosen to match the approximate proportions of the compressed reference. The installed-workspace menu has an accessible heading, radio choices, and “Select another.” The closed ASPI state and exact post-click menu are still evidence-limited. Empty state shows a disabled “Add to Slack” action and an honest configuration status if the integration is unavailable.

The video does not show how authorization works. Coke Dots uses Slack OAuth v2 as an implementation choice: the first “Add to Slack” click begins the OAuth flow; after callback, the modal shows installed workspaces and “Select a workspace” links the selected workspace to the Dot. OAuth state is one-use and bound to the signed-in user and active tenant. Bot tokens are stored in macOS Keychain under a tenant-and-team-derived entry; SQLite stores installation metadata and scopes, not the token. Only workspace owners and admins can connect or change the selection. The local E2E consent page is a mock and does not resemble or verify Slack's hosted consent screen.

This branch covers workspace installation and selection only. It does **not** receive Slack Events API messages, create tasks from Slack messages, or send Dot responses to Slack. Selecting a workspace is not evidence that Slack conversations work end to end. See [Slack OAuth v2](https://docs.slack.dev/authentication/installing-with-oauth/) and [Slack request verification](https://docs.slack.dev/authentication/verifying-requests-from-slack/).

## Verification

`npm run test:e2e` exercises a Chrome click-through using a loopback-only mock Slack OAuth provider: install ASPI, open the workspace menu, install Coke Lab through “Select another,” then switch Alpha's active Dot contact to Coke Lab. It checks the 440 × 365 dialog and 390 × 220 card at 1440 × 1000, both theme palettes, the menu's visible labels and selection, tenant isolation, owner/member permissions, distinct E2E Keychain entries, and absence of tokens from API responses and SQLite. In this pass 34 browser E2E steps and 8 cloud-computer checks passed. These checks cover local fixtures, not Slack's hosted page or a live Slack installation. The public signed-in check could not go past the configuration status because the live build lacks Slack OAuth settings.
