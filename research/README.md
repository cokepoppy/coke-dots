## Coke Dots infrastructure decisions (not Dots feature evidence)

- Pi's native transcript is persisted in each task workspace to support the official Dots continuity behavior. The use of Pi, its JSONL session format, and the `.coke-dots/pi-sessions` path are Coke Dots implementation choices, not claims about Dots internals. See [Pi session persistence](pi-session-persistence.md).
- DeepSeek Harness returns native session IDs, but a newly started SDK process cannot reattach a persisted session already restored into its runtime store. Coke Dots handles the verified duplicate-session failure by retrying once with the saved task prompt, prior result, and completed child results. A live Chrome + DeepSeek delegation run verifies this recovery; the full transcript still cannot be restored across DSH process replacement. See [DSH session recovery](dsh-session-recovery.md).
- Google accounts are keyed by the verified immutable `sub` claim; profile email remains mutable display/contact information (G1).
- Login uses an authorization-code exchange, one-time state bound to a browser cookie, PKCE, nonce validation, and verified ID-token claims (G1–G3).
- Each account gets a personal tenant. Workspace membership controls which tenant a session can select. Application data, task working directories, and computer browser profiles are tenant-scoped. Model API, Pi, and DeepSeek Harness reuse one instance-wide Keychain model credential, managed by one designated Google account.
- The supported local CLI kernels are Pi and DeepSeek Harness. They reuse the shared instance API credential; only the first Google account's `legacy` bootstrap workspace retains a host-profile fallback when no shared Model API profile is configured. Other tenants never inherit host-level CLI identities. Claude Code is deferred and cannot be selected or run. Task history and runtime profiles remain tenant-scoped. This is Coke Dots' security boundary, not evidence about OpenAI Dots.
- The active DeepSeek endpoint/model and real-task verification are recorded separately in [the credential record](deepseek-credential-record.md); the API key itself remains only in the instance Keychain.
- The Linux cloud-computer image uses Debian 13 Trixie (`node:22.23.1-trixie-slim`). R1 reports a Dots environment on Debian 13.6 x86_64; this is hands-on evidence rather than an official OS specification. The K3D E2E checks the live Pod's `/etc/os-release` and Agent Node.js version.
- Cloud Agent execution uses a stable per-run identity and a tenant-PVC result record to avoid rerunning a completed action after the Coke Dots control plane restarts. This is local recovery behavior; it does not assert that OpenAI Dots uses the same implementation.
- Workspace email invitations expire after seven days. A matching signed-in Google account must explicitly accept before membership is created; administrators can revoke pending invites. The local app does not send invitation email, so recipients must be notified separately.
- Local development remains loopback-only. The separate Mac showcase is publicly reachable only under `https://codex.cokeagent.com/dots-demo/` through its HTTPS reverse-proxy route and SSH tunnel. An initial 2026-10-07 probe found Google credentials empty; after OAuth was configured, a later login failed because the `.env`-loaded base path was evaluated before config loading, leaving the state cookie unprefixed. The fix is covered by a file-loaded-env integration test and public Chrome E2E, which now checks the secure cookie on the actual callback path. The production E2E fixture remains disabled, and existing VPS app/gateway paths keep their expected unauthenticated responses. The browser test stops before account selection. See [public demo operational evidence](public-demo-operations.md).

## Functional evidence and boundaries

- **Confirmed by current official Dots help:** Dot can take on ongoing responsibility and keep making progress between conversations; users can add details or change a request, ask for reminders or recurring checks, and review scheduled work. The help page does not define a model-selected one-time wake or checkpoint format. The reviewed videos do not show that flow. Coke Dots' persisted checkpoint, one-time Scheduled row, and same-task wake are implementation choices documented in [personal agent self-wake evidence](personal-agent-self-wake.md).
- **Confirmed:** The cloud computer has its own browser and sessions. Merely opening it does not take control; the user selects Take over and later Return control (O4).
- **Implementation choice, not an observed workflow:** Coke Dots gives its Model API, Pi, and DeepSeek Harness adapters the same read-only `open_public_page` tool for screened public HTTPS pages in the active tenant computer. Pi registers it through the SDK's custom-tool interface; DSH receives it through a task-local Cordis patch and authenticated loopback bridge. The tool pins DNS, revalidates redirects, strips active/network-capable page content, and pauses if the user takes over. ## Frame and workflow capture protocol

1. Acquire the original publicly available video through a permitted playback or download path. Keep original video under `research/videos/` (git ignored). Record URL, duration, resolution and capture date in a local manifest.
2. For each chapter lead, watch the entire transition at normal speed, then inspect frames around each state change. Record exact timecodes and click or voice action, prior state, next state and any error.
3. Extract lossless PNG frames with `ffmpeg -ss <time> -i <video> -frames:v 1 research/frames/<source>-<time>.png`. Keep frames local; store source/timecode and measurements in a tracked ledger without redistributing video frames.
4. Measure viewport, visible control bounds, spacing, color samples and text styles only where frames are sharp enough. Mark clipped or compressed values unknown. Obtain more than one frame for animation states.
5. Capture our app at the same viewport and compare overlay, changed-pixel ratio and region-level differences. Require visual review for font antialiasing and video compression artifacts.
6. Replay the observed path, including failed steps, against a local build. A screenshot match does not establish workflow parity; a successful task does not establish visual parity.

## Replay scripts

- **Setup:** create dot → inspect default name and avatar → edit visible appearance controls → rename → reopen profile → confirm persistence.
- **Persistent work:** assign a goal → close UI → let worker progress → reopen → inspect Activity → redirect priority → verify task and result history.
- **Scheduled work:** request recurrence → inspect Scheduled details → run at the requested trigger → inspect notification → cancel future run.
- **Computer:** open work computer → inspect without control → Take over → perform a browser action → Return control → verify agent resumes.
