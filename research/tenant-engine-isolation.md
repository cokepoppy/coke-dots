# Tenant boundary for host-level agent kernels

## Why this boundary exists

Pi and DeepSeek Harness are started by the Coke Dots server process. They use the API profile explicitly configured for this Coke Dots instance. The pre-authentication `legacy` bootstrap workspace keeps its old host-profile fallback when no Model API is configured; other Google tenants never inherit the Mac owner's CLI login or home-directory state. A Google sign-in creates a tenant identity; task history, agent runtime files, and computer sessions remain isolated even though model API billing uses one shared instance credential.

## Current policy

- The OpenAI-compatible Model API profile has an instance-wide endpoint, model, and Keychain key. Model API, Pi, and DeepSeek Harness reuse that profile across all personal and shared tenants. Browser responses expose only key presence, never the secret.
- Pi and DeepSeek Harness are available to every authenticated tenant when installed and the shared Model API profile is configured. Legacy tenant-specific profiles are read only during startup migration; runtime adapters never fall back to a tenant-specific key or endpoint. Startup promotes the oldest configured legacy key when no shared key exists. Only the first Google account's `legacy` bootstrap workspace may use an existing host CLI profile when no Model API profile is configured.
- Claude Code is deferred: it is hidden from the engine picker and new task/delegation requests are rejected, even if a host `claude` binary is installed. The engine identifier remains only for rendering and failing any historical persisted Claude task clearly.
- The API rejects a task against an unavailable adapter. The worker checks availability again before dispatch; authenticated tenants require the explicit instance profile. Missing-profile errors identify the shared Coke Dots instance setting rather than implying that each workspace needs its own key.
- Saving Model API settings writes one shared API key to the instance Keychain; it does not create per-tenant copies. The first owner/admin who configures the profile becomes the instance model manager; only that Google account can change it later. Migrating an older configured workspace assigns its owner as manager. Per-user credential entry is not supported.
- Pi receives the shared OpenAI-compatible model through an in-memory Pi `AuthStorage`. Its agent settings directory is isolated under `data/tenants/<tenant>/agent-runtime/pi`; native task sessions remain in the task workspace.
- DeepSeek Harness receives the shared model, endpoint, and API key in a child environment assembled from a small allowlist. Its `HOME`, `DSH_HOME`, and XDG directories point to `data/tenants/<tenant>/agent-runtime/dsh`, never the host home. The SDK replaces the child environment when `launch.env` is supplied, and upstream credential resolution gives that launch snapshot precedence over the invoking workspace `.env`; a project file cannot redirect the shared provider key. The deployment selects a DSH profile explicitly. Every profiled task receives a mode-`0600`, task-local Cordis patch that disables built-in shell, filesystem, web, subagent, and workflow tools. A task with public-page research also gets a short-lived plugin that reaches only the active tenant's existing read-only browser capability through a token-authenticated loopback bridge. Temporary files are removed after the run. Remote Debian desktop kernels retain their separate per-tenant runtime provisioning path. See the [SDK environment contract](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/client/README.md) and [Harness launch environment rules](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/util/launch-environment/README.md).

This is Coke Dots' security policy, not a claim about OpenAI Dots. User-managed login/profile setup for Pi and DeepSeek Harness is not provided; all kernels reuse the instance default while keeping tenant data and runtime directories isolated; the legacy bootstrap host-profile fallback is limited to that one workspace. See the [Pi config path implementation](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/config.ts) and [DeepSeek Harness SDK](https://github.com/deepseek-ai/deepseek-harness/blob/master/python/sdk/README.md).

## Verification

- Unit coverage checks that Model API, Pi, and DeepSeek Harness resolve the same instance credential for a second tenant without exposing its key, DeepSeek Harness does not inherit unrelated host secrets, and tenant runtime directories reject cross-tenant symlinks.
- Chrome E2E saves one instance Model API credential, runs a task from a second Google account's personal workspace, and verifies Pi and DeepSeek Harness availability there. A shared-workspace member inherits availability without gaining permission to replace the shared key. Claude Code remains unavailable and delegation to it is rejected.
- Chrome E2E also accepts Beta into a separate shared workspace and verifies tenant separation. A different personal-workspace owner and a regular shared-workspace member cannot replace the instance credential in the UI or through the API.
- `npm test` uses a dedicated Keychain service namespace, and the browser E2E gives its temporary server a random namespace so tests cannot read or modify a real instance credential.
