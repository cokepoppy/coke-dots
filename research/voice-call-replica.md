# Voice-call replica: evidence and limits

Updated 2026-10-13 on feature/voice-audio-playback-e2e.

## Reference evidence

- **Official Dots channels documentation:** [Message or call your dot](https://learn.chatgpt.com/docs/dots/channels) says a user can call from the conversation (and the desktop app can call from the Dot profile), type while talking, and continue work already assigned after ending the call. It also says Dot-initiated calls were planned after launch.
- **Official task-flow documentation:** [Get started with your dot](https://learn.chatgpt.com/docs/dots/getting-started) says users can keep talking to the Dot to add context, change priorities, or make a decision without restarting work. The voice-specific clarification interaction is not shown in the available V1/V2 frames, so the behavior below is marked as documentation-backed and E2E-verified, not frame-measured.
- **V1, 06:26:** the Chrome/YouTube composite shows a phone-style call display, avatar and name, a 0:06 elapsed timer, and Speaker, End, and Mute controls. The user begins speaking. This is a compressed composite; it does not provide source CSS measurements or a clean native desktop frame.
- **V2, 06:29 (direct Chrome replay on 2026-10-13):** the desktop conversation stays visible while a compact microphone and red hang-up control row appears at the top of the Dot context panel, above the Dot identity. The Call and Slack actions remain below the identity. This is the browser desktop call state, distinct from the portrait handset UI.
- **V2, 05:40 and 13:09:** a call is in progress beside the Dot conversation and its computer/activity context. At 13:58 a call-ended status chip is visible. These samples do not expose a full connect/end transition or the speech service.

## Coke Dots behavior implemented

- The desktop conversation's Dot context-panel Call action opens compact mute and hang-up controls while the conversation and computer/activity context remain visible. A handset layout is reserved for narrow viewports. The context panel continues to show Call, Slack, and Teams actions.
- The selected voice provider handles microphone capture and transcription. The Volcengine SeedDuplex path sends mono 16 kHz int16 PCM to the realtime session; a recognized request is submitted to the current tenant's Pi Agent running in that tenant's cloud computer. The text composer stays available during the call.
- When the task being followed reaches `waiting`, its ID is retained for the next final utterance. That utterance uses the existing tenant-scoped task-reply endpoint, resumes the same task with the original goal, and keeps the task ID. If the reply request fails, the waiting task ID is restored so the next utterance can retry it.
- While the call is open, the UI follows task state. For SeedDuplex, the task result is sent back as text with `speech_text_buffer.commit`; SeedDuplex returns 24 kHz PCM audio and the browser decodes its Float32 samples into Web Audio playback. Browser speech synthesis remains the fallback for the browser voice provider.
- Hanging up ends the persisted call session and stops call UI polling/speech; the independent background task continues in the server worker.
- The global Dot conversation merges persisted call-end events with its chat timeline in chronological order. After reload, an ended call appears as the observed purple “Me: Call ended” chip with the smaller “Optional” label; another tenant does not see that call history.
- SQLite stores call owner, workspace, start/end time, and elapsed duration. It stores no audio or raw call transcript. The recognized request is retained through the normal task instruction and activity records.
- The Volcengine route uses server-side credentials and a proxied WebSocket; a browser without microphone permission reports an actionable error while keeping the text composer usable.

## Verification and remaining gaps

- The desktop Call control was exercised through the signed-in public Chrome page after deployment. Local `npm test` passed 133 tests, the Chrome UI E2E passed 53 steps, and the cloud-computer E2E passed 8 checks. The focused SeedDuplex suite passes 14 tests, including PCM format alignment and little-endian Float32 decoding.
- A real SeedDuplex public browser playback check observed valid Float32 frames, zero decode mismatches, and completed Web Audio sources. The 2026-10-13 public acoustic replay retained a 19-second Mac speaker capture and then fed it through a fresh live SeedDuplex call. SeedDuplex recognized the spoken comparison of three example domains and their matching titles; Pi completed the resulting task. This verifies intelligible speech reached the physical speaker path. It cannot exclude a smaller amount of hiss mixed with speech; the raw provider PCM was not retained for sample-for-sample comparison. See [the acoustic evidence log](seedduplex-public-acoustic-check-2026-10-13.md).
- The known static-noise defect was a format mismatch: `session.audio.output.format.type` requested `pcm` (24 kHz float32), while the legacy TTS extension requested `pcm_s16le` (16-bit integer). The browser decoded the response as Float32. Commit `9646703` aligns both SeedDuplex fields to `pcm`, preserves `pcm_s16le` for the legacy O2.0 path, and validates the received samples before playback.
- The current public bundle and Mac demo runtime source include that fix. The acoustic capture and live ASR replay above are signed-in manual Chrome evidence, not the authenticated Playwright suite. The dedicated public voice-Agent suite still requires a separate mode-0600 test-account storage state; that file was absent, so the automated signed-in public suite was not run.
- Current screenshot: `artifacts/e2e/2026-10-12T23-16-58-496Z/screenshots/voice-call-desktop-context-panel.png`. It verifies compact desktop controls above the Dot identity and channel actions, while the responsive test separately covers the handset layout.
- The V1 phone-style composite and V2 desktop call frame are compressed. They establish distinct layouts and control placement, but not exact source-pixel measurements; the implementation records those measurements as pending rather than claiming pixel-perfect parity.
